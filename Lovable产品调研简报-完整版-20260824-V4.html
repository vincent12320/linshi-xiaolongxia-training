上下文管理策略

关键发现

Lovable 发现将所有项目文件喂给 LLM 会降低模型表现（"LLMs become more stupid when looking at too many things at once"）。因此用 LLM 自身做预处理，智能选择与当前任务相关的文件子集。

这验证了"聚焦上下文 > 完整上下文"的设计原则。官方确认

Prompt 改进与回归测试

Prompt 修改遵循严格流程：诊断问题 → 修改 prompt → 手动验证 → 对历史查询库做回归测试 → 确认无 regression → 上线。团队做过 fine-tuning 实验但目前不在核心流程中。 官方确认

深度分析：同一个 Claude，为什么 Lovable 能生成高质量 UI？

Anthropic 官方承认的问题

"You tend to converge toward generic, 'on distribution' outputs. In frontend design, this creates what users call the 'AI slop' aesthetic."

—— Anthropic 官方 Prompt Engineering 文档 (platform.claude.com)，2026.08 官方确认

Anthropic 自己承认：裸模型倾向于收敛到"分布内"的通用输出，在前端设计中表现为被用户称为 "AI slop" 的平庸审美——安全的中间值、默认字体、均匀的颜色分布、无个性的布局。

那么 Lovable 做了什么？答案不在模型层——Lovable 和 Claude 网页版用的是同一个 Claude Sonnet/Opus（Anthropic 官方案例确认）。差异 100% 来自模型之上的七层 Harness 增值的叠加效应。每一层单独贡献 10-20% 的质量提升，叠加起来就产生了"Lovable 的模型比裸 Claude 强"的用户感知。

一个第三方验证的精确对比

一个开发者做了控制变量实验：同一条 prompt，三个环境——Claude web（有 Anthropic 内置 frontend-design skill）→ Claude Code 裸跑 → Claude Code + frontend-design plugin。结果：有 skill/plugin 的版本显著优于裸跑版——三种 Google Fonts、boot sequence 动画、noise texture 效果 vs 纯系统 monospace 的基础布局。同一个模型，有无 design skill 的差异是巨大的。

来源: baremetaldigest.substack.com 第三方验证

七层 Harness 增值拆解

Lovable 七层 Harness 增值全景

L1: shadcn/ui 组件库约束 — 质量差异的最大单一来源

当你在 Claude 网页版说"给我做一个 dashboard"，Claude 需要从零开始做无穷决策——什么组件库、颜色体系、间距规则、字体？模型选择"安全中间值"，输出就是 AI slop。Lovable 的做法：所有 UI 必须从 shadcn/ui 组件合成——模型的任务从"从空白画布创作 UI"变成"从已知美观组件中选择和组合"。

🎨 预设计美观组件
shadcn/ui 的 Button、Dialog、Form、Card 等自带精致设计、无障碍支持、键盘导航、ARIA。模型只需合成，无需发明。
📐 固定间距与排版
Tailwind 的 spacing scale（4px 基准网格）和 typography scale 消除了"padding 12 还是 16"的决策。p-3 vs p-4 就是答案。
📊 训练数据优势
shadcn/ui 是 GitHub 114K+ Stars 项目。Claude 训练数据中有海量 shadcn 用法，模型对这套库的"理解"远深于其他选择。
🧩 合成 > 创作
约束越多，输出越可控越一致。范式从"自由创作"变为"受控合成"，这是 Lovable 质量的根本来源。

L2: Design Token 系统

所有 shadcn/ui 组件引用 CSS 变量（--background, --primary, --radius…），零硬编码值。改一个 token，全局所有组件自动跟随。主题切换只是数据变更而非样式重写。裸模型会在不同组件中使用不同的硬编码颜色值——Design Token 系统杜绝了这种不一致性。

L3: Design System 强制执行引擎 — 最被低估的 Harness 层

Lovable Design System 功能 (docs.lovable.dev/features/design-systems) 官方确认

Lovable 的 Design System 不是被动参考——是带有强制执行机制的活系统：

① 集中式 Truth Source：组件、token、样式统一来源，本身是一个可编辑的 Lovable 项目
② 自动验证 Wiring：每次连接/更新后自动检查 build config、CSS imports、theme providers、dependencies
③ 偏离检测（关键）：Agent 在编码过程中主动捕获——raw colors（硬编码颜色）、custom components（应用 Design System 的地方自建组件）、其他偏离行为
④ 跨项目同步：一键更新所有已连接项目

⚠ 这是裸模型做不到的核心原因：Claude 网页版不会检查"颜色是否在 token 体系内"、"组件是否符合 Design System"。Lovable 的 Agent 在每轮编码中内嵌这个审查。

L4: System Prompt 精密工程

Lovable 官方 prompting docs 要求用户提供 5 层信息——High-Level Description → Look & Feel（情绪审美）→ Brand Guidelines（精确到字体、颜色 hex）→ UI Library → Feature Details。Lovable 的 System Prompt 很可能已内置了这 5 层的 default 值，当用户只说"做一个 dashboard"时，prompt 已替用户填充了审美方向和组件约束。裸 Claude 没有这些 defaults，所以输出平庸。未公开/推测

L5-L7: Context Hydration + 实时预览 + 回归测试

这三层在前文③-b 中已详述。核心要点复述：L5 用小模型预筛选上下文（"LLMs become more stupid when looking at too many things at once"）；L6 实时预览创造秒级纠偏反馈循环；L7 回归测试确保 prompt 改进只升不降。ZenML 案例

MCP Server（品类唯一的一方 MCP）使 Lovable 应用可被任何 AI 助手调用 → 20+ Connectors（Stripe/Notion/Shopify/Slack） → Google Cloud Marketplace 上架 → Lovable 2.0 多人实时协作。从个人工具 → 团队平台 → AI Agent 生态中的应用层。

⑥ 对林氏小龙虾 & 专家套件的启示

Harness 设计：简单可靠优于复杂自主

Lovable 最值得借鉴的技术决策：对复杂 Multi-Agent 架构的明确拒绝。"快模型预处理 → 一次大模型主调用 → 快模型后处理"的 3-step 链路，在准确率、速度、可理解性上全面优于复杂多 Agent 通信系统。

→ LinsyWork 映射：双引擎（LangGraph + Claude Agent SDK）可借鉴 Hydration Pattern——用轻量模型做知识库/历史对话的上下文筛选，再将精选上下文交给主模型推理。比全量灌入上下文窗口更有效。
Plan-then-Execute 双阶段 Checkpoint

Plan Mode → Build Mode 将"理解意图"和"执行操作"解耦，中间插入人工批准点。计划物化为 .lovable/plan.md 可编辑文件。Plan 用 Opus 4.5（强推理），Build 用 Sonnet（快编码）。

→ 专家套件映射：与三态输入模式（default/plan/ask）高度对应。可借鉴：① Plan 阶段输出为可编辑结构化文档（比纯对话确认更有确定性）；② 按模式分配不同模型是低成本提升体验的好策略。
Opinionated Stack 约束解空间

LLM 在受约束的模式空间中生成的可靠性远高于自由发挥。模板库、组件库、设计模式全部固定后，prompt 优化和回归测试的 ROI 才能真正叠加。

→ Skill 架构映射：每个 Skill Package 就是一个 opinionated stack。Lovable 的经验说明，越是约束清晰的 Skill，模型执行可靠性越高。进一步验证了 R&D 模板标准化（plugin.json 16 字段、SKILL.md frontmatter 4 字段）的方向正确性。
Vibe-Coding 交互范式的产品化要素

Lovable 验证的三个范式要素：自然语言作为编程语言、对话作为开发环境、实时预览作为反馈循环。

→ LinsyWork 映射：① "边生成边渲染"的透明度——Skill 执行长任务时逐步展示中间结果而非等最终输出；② Visual Edit 作为 prompt 节省器——在 artifact panel 支持直接编辑生成结果的结构化字段，减少"帮我改一下XX"的对话轮次。
评测基础设施是 Agent 产品的安全网

Lovable 的 prompt 改进必须对历史查询库做回归测试。创始人公开说"挑战任何竞品，赌 $1000 证明他们不是最好的"——这种自信来自系统化的评测能力。

→ 评测框架映射：与我们的 200 题知识库数据集、三版对比评估、证据报告标准方向一致。Lovable 的经验说明，在 Agent 产品中，评测基础设施的投资回报极高——它是 prompt 工程和模型切换的安全网。

实施路线图建议

分三阶段复现 Lovable 核心能力

P1

Phase 1: Skill Package 基础版（2-3 周）

核心价值：用 prompt 约束复现 Lovable 的 UI 质量

① 编写 SKILL.md：技术栈约束 + Design Token 规则 + 合成模式指令 + 审美方向 defaults + 偏离自检
② 制作脚手架模板：vite-react-shadcn 项目模板（含 globals.css、tailwind.config、shadcn 组件目录）
③ 编写 Plan Mode 和 Build Mode 的分阶段 prompt 模板
④ 在 LinsyWork 中注册为 Skill，验证"describe → generate → preview"基本流程

P2

Phase 2: Harness 层增强（3-4 周）

叠加 Context Hydration 和 Design System 检查

① Hydration Pattern：轻量模型做 file relevance scoring → top-K 选取
② Reviewer SubAgent：生成后自动检查 token 偏离、组件一致性
③ 回归测试基线：20-30 个典型 UI 生成用例建立评测数据集
④ Plan→Build 双模式 Skill 路由优化（Plan 用强推理，Build 用快编码）

P3

Phase 3: 平台级能力（需跨团队协作）

超出 Skill 范畴，需平台/前端支持

① LinsyWork client 嵌入 iframe sandbox 实时预览生成的 React 代码
② Visual Editor：预览中点选修改，不消耗 prompt 轮次
③ GitHub 同步 + 一键部署（可作为 Connector 实现）

优先级：P1 完成即可验证核心假设——"通过 Skill 约束，LinsyWork 能否生成 Lovable 级别的 UI"。如果 P1 验证成功，说明 Harness 前四层（组件库 + Token + System Prompt + 自检）是质量差异的主要来源，P2/P3 ROI 可预期。如果不足，需回到 Lovable 未公开的 prompt 工程策略做更深挖掘。
